● I reviewed the Codex comments on PR #25. Both were P1 and both were real —
  they targeted the owner-key fix I'd written in the previous round.

  Finding 1: lowercasing the whole server URL

  Scheme and host are case-insensitive; a path is not. normalizeBaseUrl keeps
  whatever path you configure and Retrofit supports path-based base URLs, so
  https://host/TTSRoad/ and https://host/ttsroad/ are two deployments — and they
  collapsed to one owner key. Two people with the same username on those
  instances would have read and dismissed each other's history.

  The same reasoning applies to the username, which Codex didn't raise. It's
  stored as response.user.username — the server's own spelling — so folding it
  bought nothing and merged two genuinely distinct accounts on a case-sensitive
  server (Django's default). Both are now unfolded.

  The rule I settled on and wrote into the code: merging two identities is far 
  worse than splitting one. A split costs a lost strip; a merge discloses one
  person's reading to another.

  Finding 2: resolving the owner too late

  recordHistory read the live session, but it runs after a suspending progress
  save, and stop() is fire-and-forget. If account A signed out and B signed in
  during that window, A's chapter titles were filed under B's key — exactly the
  disclosure the owner key exists to prevent. The owner is now captured
  alongside the queue it belongs to, and cleared with it.

  The part that mattered most

  That same identity flaw existed in Phase 7's StorageIdentity, and there it's 
  worse. canonicalOrigin dropped the path entirely, so two path-based
  deployments on one host shared a download directory — meaning one server's
  audio served for another server's chapter, which is precisely the acceptance
  criterion that says overlapping content must never collide. accountKey folded
  the username the same way. Both fixed, with the split-vs-merge rule written
  down where the decision is made.
